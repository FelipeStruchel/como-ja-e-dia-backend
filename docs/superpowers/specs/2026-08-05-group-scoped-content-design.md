# Group-scoped content — Events, Schedules, Persona, Triggers (sub-project 2 of 4) — Design

**Goal:** Make Events, Schedules, and Persona group-aware (each can target one group, several, or — `super_admin` only — every group), fix the pre-existing gap where `Trigger` already has `groupId` but its routes still check the global `bom_dia_admin` role, and retire the legacy global `bom_dia_admin` role once every route that depended on it has migrated.

This is sub-project 2 of 4 from `2026-08-04-group-scoped-admin-design.md`'s roadmap. Sub-project 1 (merged) built the foundation: `GroupAdmin` table, `isGroupAdminOf`/`getAdminGroupIds`, `requireGroupAdmin` middleware, admin-assignment UI. Nothing from sub-project 1 is wired into a real route yet — this sub-project is the first to actually use it.

## Security constraint (applies to every task below)

**The backend never trusts a `groupId` the client sends just because the client's own UI only offered valid-looking options.** Every route that accepts a `groupId` — create, update, delete, or the "apply to N of my groups" flow — re-validates it server-side via `requireGroupAdmin` (or, for confessions in the companion sub-project 3, via a fresh flag lookup). There is no bulk-create endpoint that accepts an array of `groupId`s from the client and loops over them internally — "apply to all my groups" in the UI means the frontend issues one independent request per group, and each one is independently authorized. A client that has stale or tampered UI state cannot get a request through that the server wouldn't have allowed one at a time.

## Decisions from brainstorming

**Data model — nullable `groupId`, null = "every group," `super_admin`-only:**
- `Event.groupId String?`, `Schedule.groupId String?`, `PersonaConfig.groupId String? @unique` — matching sub-project 1's convention (a scoped `bom_dia_admin` always attaches a resource to one or more of their own groups explicitly; `groupId = null` is reachable only because `requireGroupAdmin`'s `super_admin` bypass runs before the null-check, so only `super_admin` can create/leave a resource unscoped).
- `Trigger.groupId` already exists as a **required** `String` (not nullable) — every trigger has always been tied to exactly one group by nature (it fires on incoming messages from that one WhatsApp group; there's no "broadcast trigger" concept). No schema change needed there, only the auth wiring.

**Migration / backfill:**
- Existing `Event` and `Schedule` rows get their `groupId` backfilled to the main seed group (same one `ensureMainGroupSeeded()` creates), matching sub-project 1's "avoid a B.O." rule for pre-existing data.
- The existing `PersonaConfig` row is the one exception: its `groupId` stays `null`. It keeps acting exactly as it does today — the fallback persona for any group that has no persona of its own — rather than becoming one specific group's persona. A group with no `PersonaConfig` row of its own falls through to the `groupId = null` row, then to the hardcoded `AI_PERSONA_DEFAULT` if even that doesn't exist. Only `super_admin` may edit the `groupId = null` row (same "only super_admin touches the unscoped resource" rule as everything else).
- New `Group.eventsEnabled Boolean @default(false)` column (Events had no corresponding feature flag before; every other group-scoped resource type gets its own toggle, so this adds the missing one for consistency). `ensureGroupSeeded` sets it `true` for the main group like the other five flags.

**`requireGroupAdmin` fix (small, in `middleware/auth.ts`):** the existing "resolved `groupId` is null" branch returns `400 { error: "groupId é obrigatório" }` today. Change to `403 { error: "Sem permissão para operar fora de um grupo específico" }`. Reasoning: by the time a non-`super_admin` reaches that branch, the request would have succeeded for a `super_admin` with the exact same payload — the failure is about *who is asking*, not a malformed request. This covers both cases uniformly: a scoped admin omitting `groupId` on create, and a scoped admin trying to update/delete a resource that already has `groupId = null`. This is the first and only consumer of `requireGroupAdmin` so far, so it's the right time to fix it — no route depends on the old 400 today.

**AI caption generation — avoid needless duplicate Gemini calls, but don't over-engineer:** `generateAICaption` is called from exactly one place, `processScheduleJob` in `services/scheduledJobs.ts`, and it's the only fan-out-to-multiple-groups AI call site in the codebase (`generateAIAnalysis`, used by `!analise`, is always scoped to the single group that sent the command — no fan-out concern). Of `generateAICaption`'s inputs, only two can plausibly differ per target group: the events-derived fields (`names`, `eventsTodayDetails`, `nearestDateStr`, `countdown`) and the persona (`personaOverride` falls back to the group's resolved persona only when `schedule.personaPrompt` is empty). Everything else (`dayOfWeek`, `todayDateStr`, `greetingHint`, `announceEvents` itself) is identical for every target group of one schedule run. Algorithm:
- If `schedule.announceEvents` is `true`: generate one caption **per target group**, using that group's own `buildEventsContext(groupId)` and resolved persona. No bucketing — once events are genuinely per-group, two groups sharing an identical events picture on the same day is rare enough not to special-case.
- If `schedule.announceEvents` is `false`: `eventsContext` is the same constant "no events" shape for every group (exactly like today — `buildEventsContext` isn't even called in this branch). The only remaining source of variation is persona. Group the target groups by their **resolved persona text** (a schedule-level `personaPrompt` override, if set, makes every target group land in the same bucket automatically, since it doesn't depend on `groupId` at all). Generate one caption per unique bucket, reuse it for every group in that bucket.

**New `GET /groups/mine` endpoint — the picker's data source.** Gap found during design: the frontend pickers described below need each eligible group's **name and feature flags**, not just its id. `/auth/me` only returns `adminGroupIds: string[]` (ids only, from sub-project 1), and the existing `GET /groups` is `super_admin`-only (sub-project 1, unchanged) — a scoped `bom_dia_admin` has no way to fetch their own groups' names/flags today. New route in `routes/groups.ts`: `GET /groups/mine`, `requireAuth` only (no role restriction — every authenticated user gets *some* answer, even if empty). Returns every `Group` field (`id, name`, all six feature flags) for: every group in the system if the caller is `super_admin`, or exactly the groups in their `adminGroupIds` otherwise. This one endpoint backs every picker in this sub-project (Events/Schedules/Triggers filter the response by their own flag client-side; a future Persona group-switcher would use it unfiltered) — no need for a separate flag-specific endpoint per resource.

**List endpoints (`GET /events`, `GET /schedules`, `GET /triggers`) — filtered, not gated by a single `requireGroupAdmin` check:** these aren't single-resource operations, so `requireGroupAdmin(getGroupId)` (which needs exactly one `groupId`) doesn't apply. Instead: `requireAuth` only (the `requireRole("bom_dia_admin")` these routes have today is being retired along with the rest of the global role), then filter server-side in the Prisma query: `super_admin` gets every row; anyone else gets `WHERE groupId IS NULL OR groupId IN (<their adminGroupIds>)` — visible (read-only) into whatever's been broadcast globally, plus full read/write on their own groups' items (write access is separately enforced per-item by `requireGroupAdmin` on the mutating routes). `GET /events` specifically is public/unauthenticated today; it becomes authenticated as part of this change, since filtering by "the caller's groups" requires knowing who's calling, and it was only ever consumed by the admin management page anyway (verified: no other consumer exists).

**Events become genuinely per-group in the content they produce:** `buildEventsContext(tz)` becomes `buildEventsContext(tz, groupId)`, filtering `WHERE (groupId = $groupId OR groupId IS NULL) AND date ...` — a group sees its own events plus anything a `super_admin` broadcast globally.

**Schedule fan-out target resolution changes from "every `scheduledGreetingsEnabled` group" to "this schedule's own group(s), still gated by the flag":**
- `schedule.groupId` set → target is that one group, but only if it currently has `scheduledGreetingsEnabled = true` (the flag remains a per-group kill switch independent of which schedules exist).
- `schedule.groupId = null` (`super_admin` only) → target is `getScheduledGreetingsEnabledGroupIds()`, i.e. today's exact behavior, unchanged.

**Frontend — one picker rule for every "who does this apply to" UI, not a role-based rule:**
- `eligibleGroups` = `super_admin` ? every group in the system : the groups this user administers (from `adminGroupIds`, already returned by `/auth/me` since sub-project 1).
- 0 eligible groups → creation is blocked with an explanatory message (an admin of nothing can't create group-scoped content).
- 1 eligible group → no picker shown; that group is the implicit target.
- 2+ eligible groups → picker shown (to *any* admin who reaches this branch, `super_admin` or not — the picker's presence depends on how many groups you reach, never on which role you hold), with a "select all of mine" convenience that pre-checks every eligible group. Only `super_admin` additionally sees a distinct "broadcast to all groups (including future ones)" action — a materially different operation (creates one `groupId = null` row) from "select all N groups I can currently see" (creates N explicit rows, which would *not* automatically extend to a group registered after the fact). The UI must not conflate these two.
- Each eligible-groups list is itself filtered by the resource's own feature flag: the Schedules picker only offers groups with `scheduledGreetingsEnabled = true`, Triggers only `triggersEnabled = true`, Events only `eventsEnabled = true` (new flag, see above). Persona has no such flag — every group implicitly supports having a persona.
- Persona's UI shape is different in kind from the other three: it's not a creatable list, it's one editable value per group (with the `groupId = null` row being the global fallback, `super_admin`-only to edit). The persona page becomes a group-switcher (same `eligibleGroups` rule, but selecting one group to view/edit rather than multi-selecting targets for a new row) plus, for `super_admin`, the option to edit the global fallback.

**Final step, only after every route above has migrated:** delete the `UserRole` rows where `role.slug = 'bom_dia_admin'` (per sub-project 1's design, these were left in place specifically to avoid a lockout window — this is that migration's endpoint). Leave the `Role` row itself; it becomes unreferenced but harmless.

## Testing

- `groupService.ts`: confirm `ensureGroupSeeded` sets `eventsEnabled: true` alongside the other five flags.
- `GET /groups/mine`: `super_admin` gets every group; a scoped admin gets exactly their `GroupAdmin` rows' groups (full flag set, not just ids); a user administering nothing gets `[]`, not an error.
- `requireGroupAdmin.test.ts`: update the existing 400 assertion to 403, add a case distinguishing "missing on create" vs "existing resource is global" both landing on 403.
- Per-resource route tests (events/schedules/triggers): auth wiring (mutating routes use `requireGroupAdmin`, not `requireRole`), list-endpoint filtering (super_admin sees all; scoped admin sees own + null; a group not in either set is invisible), and the null-groupId-requires-super_admin path on create.
- `scheduledJobs.test.ts` (new or extended): the announceEvents=true branch calls `generateAICaption` once per target group with that group's own events context; the announceEvents=false branch buckets by resolved persona and calls `generateAICaption` once per unique bucket, not once per group.
- `personaConfig.ts`: `getPersonaPrompt(groupId)` resolution order — group-specific row → `groupId = null` row → hardcoded default — each level tested independently.
